# Demand Radar

Портал, который мониторит доски объявлений, Telegram-чаты и форумы, и сводит
**две стороны сделки**:
- **Спрос** — сообщения вида "ищу X, не могу найти" (раздел "Спрос" на Kufar и т.п.)
- **Предложение** — сообщения вида "отдам X даром/почти даром" (giveaway-объявления
  в общей ленте, отсеиваются по ключевым словам)

Обе стороны классифицируются через LLM в один и тот же список категорий (см.
`pipeline/categories.py`, взят из реальной структуры категорий Kufar), после чего
`/matches` показывает пары "кто-то отдаёт X дёшево — кто-то в этой же категории
готов платить" — это и есть готовые арбитражные возможности.

Сделан для двух сценариев одним и тем же интерфейсом:
1. Личный анализ рынка (сейчас) — без авторизации, ты единственный пользователь.
2. Будущий SaaS для предпринимателей — таблицы `users`/`saved_watches` и роуты
   авторизации уже заложены в схему и закомментированы в `app.py`, включаются без
   переписывания дашборда.

## Архитектура

```
collectors/         источники данных (Kufar, Telegram, форумы) — каждый новый
                     источник = новый класс BaseCollector или конфиг для forum_generic.
                     Один и тот же коллектор может быть источником и спроса, и
                     предложения одновременно — тип задаётся в sources.signal_type.
pipeline/
  categories.py        единый список категорий для обеих сторон (иначе не свести в /matches)
  prefilter.py         дешёвый regex-фильтр для спроса ("куплю", "ищу"...)
  prefilter_supply.py  дешёвый regex-фильтр для предложения ("отдам", "даром"...)
  classifier.py         LLM-классификация (OpenRouter) — отдельные промпты для
                         спроса и предложения, общий список категорий
  aggregator.py        сборка недельных трендов по категориям (сторона спроса)
db/                  SQLite-схема и слой доступа (легко переносится на Postgres)
templates/, static/  веб-дашборд (Flask): /, /category/<name>, /matches
run_pipeline.py      CLI: collect / filter / classify / classify_supply / matches / trends / all
seed_sources.py      первичная регистрация источников
app.py               сам веб-портал
```

## Запуск (Termux)

```bash
pip install -r requirements.txt
export OPENROUTER_API_KEY="твой бесплатный ключ с openrouter.ai/keys"

python seed_sources.py        # регистрирует источники (один раз, потом отредактируй под себя)
python run_pipeline.py all    # собрать -> отфильтровать -> классифицировать (обе стороны) -> тренды
python app.py                 # портал на http://127.0.0.1:8080
```

Дальше `run_pipeline.py all` вешается на cron/Termux:Boot с интервалом 2-6 часов,
чтобы данные обновлялись сами. `/matches` наполняется по мере накопления данных
с обеих сторон — на старте, скорее всего, будет пусто, это нормально.

## Что нужно донастроить перед первым реальным запуском

1. **Kufar (спрос)** — рабочий каркас есть, парсит раздел "Спрос" по HTML.
2. **Kufar (предложение)** — парсит общую ленту всех категорий Минска и отсеивает
   giveaway-объявления по ключевым словам. Так как отдельной рубрики "Отдам даром"
   у Kufar нет, это менее прицельно, чем сторона спроса — ожидай больше шума.
3. **Telegram** — нужен свой `api_id`/`api_hash` с https://my.telegram.org и имя
   реального чата в `seed_sources.py`. Первый запуск попросит код из Telegram —
   это создаст `.session`-файл, дальше без логина.
4. **Форумы** — `forum_generic` работает через CSS-селекторы, которые надо один раз
   свериться с реальной вёрсткой конкретного раздела (может отличаться от примера).

## Известные ограничения matching-логики (MVP)

- Категории сравниваются точным совпадением строки (без учёта регистра) — если
  модель классифицировала одно как "Электроника", а другое как "Бытовая техника",
  хотя по смыслу это одно и то же, пара не найдётся. Можно улучшить позже через
  эмбеддинги/similarity вместо точного совпадения.
- Совпадение по категории не гарантирует совпадение по конкретному товару —
  "отдам старый холодильник" и "куплю телевизор" оба попадут в "Бытовая техника".
  Финальная проверка релевантности — на человеке.
- Регион пока не учитывается в матчинге (только Минск на старте) — для других
  городов нужно добавить отдельные источники с фильтром по региону.

## Кандидаты источников "на потом" (не реализовано, но встраивается по тому же интерфейсу)

- VK-группы "барахолка/куплю-продам" — есть официальный API, добавляется проще всего
- Instagram/Facebook Marketplace — нужен Playwright + логин, ToS жёстче
- Avito-подобные локальные доски
- vc.ru / отраслевые форумы — для B2B-спроса, а не только потребительского
- Отзовики — люди жалуются на отсутствие товара/сервиса как альтернативный сигнал

## Юридический момент

Для личного анализа риск минимальный. Если дальше продаёшь инсайты клиентам —
агрегируй так, чтобы не было прямых цитат/привязки к конкретным авторам сообщений,
только статистика по категориям спроса.
